# UAAF v2.6 — Confidential Federation Transport & Key Agreement

**Status:** Extension Release
**Version:** 2.6.0
**Extension ID:** UAAF-FED-2.6
**Profile:** Full only
**Depends on:** UAAF v2.4 protocol negotiation + v2.5 authenticated transport

## 1. Purpose

UAAF v2.6 adds confidentiality to the v2.5 federation channel without changing the authority, delegation, policy, or protocol-negotiation semantics already established by UAAF v2.0–v2.5.

The reference implementation uses:

- X25519 ephemeral key agreement;
- HKDF-SHA256 key derivation;
- ChaCha20-Poly1305 AEAD;
- per-channel key epochs;
- per-direction key and nonce derivation;
- authenticated rekey;
- deletion of obsolete local ephemeral key files after successful rekey.

The implementation is transport-agnostic and uses filesystem-backed envelopes as its reference carrier.

## 2. Security Boundary

v2.6 provides:

- confidentiality of message payloads;
- integrity and authenticity via AEAD plus the existing Ed25519 trust model;
- channel binding;
- protocol-contract binding;
- peer and project identity binding;
- sequence-based replay protection;
- authenticated key epochs;
- authenticated reconnect/rekey semantics.

v2.6 does **not** claim:

- traffic-analysis resistance;
- metadata confidentiality;
- availability guarantees;
- endpoint compromise resistance;
- memory zeroization guarantees from a Python implementation;
- a blanket formal forward-secrecy guarantee under every endpoint-compromise model.

The design is **forward-secrecy-oriented** through fresh ephemeral X25519 material per key epoch. Old local key files are removed after successful rekey, but normal Python process memory is not a secure zeroization boundary.

## 3. Preconditions

A secure channel requires all of the following:

1. Full-profile UAAF project.
2. Active v2.4 protocol contract.
3. `confidential-transport` negotiated as an enabled feature.
4. Trusted peer root pinning.
5. Valid Ed25519 identity/signature material.
6. Secure transport configuration enabled.

Missing prerequisites result in `NOT_CONFIGURED` or a fail-closed denial, depending on the command and context.

## 4. Cryptographic Construction

For channel `C`, epoch `E`:

```text
X25519(ephemeral_local, ephemeral_remote)
                ↓
          shared secret
                ↓
       HKDF-SHA256 with
   channel/contract/epoch binding
                ↓
     directional key material
                ↓
 ChaCha20-Poly1305 AEAD payloads
```

Separate directional material is derived for initiator→responder and responder→initiator. Each direction receives its own nonce prefix and sequence space.

## 5. Channel Lifecycle

```text
OPEN
 ↓
ACCEPT
 ↓
CONFIRM
 ↓
OPEN
```

Only an `OPEN` channel may carry application payloads.

The open/accept/confirm records remain signed under the v2.5 trust model and include distinct peer identity and project identifiers.

## 6. Message Processing

Sender checks, in order:

```text
current protocol contract
↓
channel state
↓
peer root pin
↓
peer/project binding
↓
sequence allocation
↓
AEAD encryption
↓
outbox write
```

Receiver checks, in order:

```text
current protocol contract
↓
channel state
↓
sender/project binding
↓
sequence validity
↓
peer root trust
↓
AEAD authentication
↓
plaintext release
```

Plaintext must not be written to the message envelope.

## 7. Nonce Construction

The reference implementation derives a four-byte nonce prefix per direction and combines it with an eight-byte monotonically increasing sequence value for a 12-byte ChaCha20-Poly1305 nonce.

Nonce uniqueness is therefore a protocol invariant. Reusing a sequence within the same epoch is a protocol error.

## 8. Associated Data

AEAD associated data binds the ciphertext to:

- protocol contract hash;
- channel ID;
- epoch;
- sender peer ID;
- sender project ID;
- receiver peer ID;
- receiver project ID;
- direction;
- sequence number.

Tampering with any bound field invalidates authentication.

## 9. Rekey

Rekey is an authenticated epoch transition:

```text
E
↓
new ephemeral exchange
↓
new key derivation
↓
peer confirmation
↓
E+1 active
↓
obsolete local ephemeral key removed
```

A channel must not silently accept a peer-root change or contract-hash change as part of rekey.

## 10. Replay and Ordering

Sequence state remains monotonically increasing per direction and epoch. Old, duplicated, or out-of-order payloads are rejected.

A resumed/rekeyed channel does not reset sequence protections without creating a new authenticated epoch.

## 11. Filesystem Namespace

```text
.ai/federation/secure/
├── CHANNELS/
├── INBOX/
├── OUTBOX/
├── keys/
├── AUDIT.jsonl
├── CONFIG.yaml
├── README.md
└── SECURITY-MODEL.md
```

Private ephemeral keys under `keys/` are runtime-sensitive material and are ignored by the project `.gitignore` generated by UAAF.

## 12. CLI

```bash
python tools/uaf.py federation-confidential open ./project ...
python tools/uaf.py federation-confidential accept ./project ...
python tools/uaf.py federation-confidential confirm ./project ...
python tools/uaf.py federation-confidential send ./project ...
python tools/uaf.py federation-confidential receive ./project ...
python tools/uaf.py federation-confidential rekey ./project ...
python tools/uaf.py federation-confidential rekey-accept ./project ...
python tools/uaf.py federation-confidential rekey-confirm ./project ...
python tools/uaf.py federation-confidential check ./project
```

## 13. Conformance

UAAF-C v2.6 checks:

- Full profile requirement;
- manifest protocol declaration;
- secure namespace presence;
- cryptographic configuration;
- active v2.4 contract requirement;
- negotiated feature requirement;
- open-channel schema;
- runtime key protection.

A fresh, un-negotiated project should report the secure transport as `NOT_CONFIGURED`, not as a broken configuration.

## 14. Compatibility

v2.6 is cumulative when explicitly selected. Installing v2.5 or earlier does not silently create the confidential namespace.

Downgrading from v2.6 removes only generated v2.6 artifacts; user-created content is preserved.
