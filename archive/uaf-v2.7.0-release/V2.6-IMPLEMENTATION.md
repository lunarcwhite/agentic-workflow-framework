# UAAF v2.6 — Implementation Notes

## Implemented

- `tools/uaf_federation_confidential.py`
- unified CLI `federation-confidential`
- v2.6 initializer support
- secure namespace creation
- v2.4 capability negotiation integration
- v2.6 conformance checks
- compact v2.6 doctor path
- private-key `.gitignore` protection
- rekey epoch management
- directional key/nonce derivation
- channel contract and peer-root binding

## Cryptographic Stack

```text
Identity / trust:      Ed25519 (existing v2.5/v1.9 trust layer)
Key agreement:        X25519 ephemeral keys
KDF:                  HKDF-SHA256
AEAD:                 ChaCha20-Poly1305
Epoch model:          per-channel authenticated rekey
```

## Reference Carrier

The implementation stores channel state and encrypted message envelopes on the filesystem. This is intentionally a reference carrier rather than a claim that filesystem exchange is a production network transport.

## Key Handling

Ephemeral private keys are stored only below:

```text
.ai/federation/secure/keys/
```

The generated `.gitignore` prevents these files from being committed. After successful rekey confirmation, obsolete epoch key files are removed.

The Python implementation does not provide guaranteed process-memory zeroization; deleting the file is therefore a storage hygiene measure, not a proof of complete cryptographic erasure.

## Contract Binding

Every message operation checks the currently active v2.4 protocol contract hash. This prevents an old channel from remaining usable after the negotiation contract changes.

## Peer Binding

Both peer ID and project ID are carried separately. A valid cryptographic signature is insufficient when the identity is bound to the wrong project/channel.

## Diagnostic Semantics

Fresh projects report:

```text
secure transport = NOT_CONFIGURED
```

This is a healthy, expected state when negotiation has not yet established an active v2.4 contract with the confidential-transport feature.

## Test Harness Note

The dedicated v2.6 suite is executed with fresh-process/per-test isolation because the cumulative cryptographic/subprocess suite can exceed the execution harness time limit when run as one process. The underlying scenarios are therefore validated independently rather than inferred from a partial combined run.
