# UAAF v2.8 — Implementation Notes

UAAF v2.8 separates key custody from key lifecycle and transport. The reference implementation adds a provider registry, non-secret key references, provider health, and a custody audit namespace.

## Providers

`filesystem` is the only provider bundled as immediately available. `os-keychain` is enabled only when a compatible Python `keyring` backend is installed. `kms` and `hsm` are represented through an external adapter health contract; vendor-specific cloud/HSM clients are not bundled.

## Safety

The provider policy enforces:

- `secret_export: DISABLED`
- `private_key_return: DISABLED`
- fail-closed when the active provider is unavailable
- no implicit filesystem fallback

Provider health output never contains private key material.

## CLI

```bash
python tools/uaf.py key-storage check <project> --json
python tools/uaf.py key-storage inventory <project> --json
python tools/uaf.py key-storage set-active <project> --provider filesystem --json
python tools/uaf.py key-storage register <project> --key-id KEY-001 --provider kms --purpose federation-signing --json
```

`set-active` requires the provider health state to be `PASS`. `register` stores metadata only.

## Adapter boundary

The reference build does not impersonate a cloud KMS/HSM implementation. A production adapter must implement a non-secret health operation and a provider-specific signing/key-custody API outside the UAAF repository. UAAF only defines the contract, policy, and integration boundary.
