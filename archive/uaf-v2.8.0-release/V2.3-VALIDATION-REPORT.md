# UAAF v2.3 Validation Report

## v2.3 scenarios

`10/10` scenarios verified with fresh-process execution. The combined file runner is not used as the acceptance metric because subprocess-heavy test execution in this environment can stall after already-completed tests.

Coverage includes:

1. v2.3 initializer and manifest
2. restrictive action/risk/evidence intersection
3. deny-first remote denial
4. approval monotonicity
5. authorized enforcement after negotiation
6. risk escalation denial
7. signature/evidence requirement denial
8. disjoint-domain denial (`domain_scope: NONE`)
9. v2.3 conformance and compact doctor
10. v2.2 downgrade removes v2.3 namespace

## Compatibility

- Core UAAF tooling: `12/12` verified (11 completed in suite plus the doctor scenario verified separately after the suite-level harness stall).
- v2.2 federation intelligence: `7/7` passed.
- v2.3 field archetypes: `1/1` passed across five archetypes.

## Important hardening

The domain contract explicitly distinguishes `ALL`, `SET`, and `NONE`. Two constrained peers with disjoint domains therefore produce a denied contract instead of an empty list that could be misread as unrestricted.

## Known harness limitation

Some whole-suite pytest invocations may stall because several tests spawn nested Python/crypto subprocesses. Fresh-process per-test validation is used for affected cases, with exit codes recorded from the individual tests.
