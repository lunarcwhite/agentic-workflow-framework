# UAAF v1.1 Evolution Proposal

Status: Draft for implementation design
Base protocol: UAAF v1.0

## Objective

v1.1 should improve context accuracy, observability, coordination, and maintenance without changing the normative meaning of UAP/IRE/CLE/APRE/ASE/VEE/MEE/RCE in v1.0.

## Proposed additions

### 1. Capability Override Contract

Auto-detection remains advisory. Add an explicit override layer:

```yaml
capabilities:
  frontend:
    detected: true
    override: null
    confidence: HIGH
```

Possible override states:

```text
auto
force_true
force_false
review_required
```

The override should be traceable to a user or project decision.

### 2. Context Impact Graph

Use changed paths, source ownership, task domains, and references to estimate which knowledge needs retrieval or review.

```text
CHANGE
→ IMPACT GRAPH
→ AFFECTED KNOWLEDGE
→ TARGETED RETRIEVAL
→ FRESHNESS REVIEW
```

The graph should be advisory before it becomes a hard gate.

### 3. Memory Compaction

Add explicit cluster/consolidation metadata so repeated memories can be merged without losing provenance.

```text
MEMORY CLUSTER
→ DEDUP
→ MERGE
→ PRESERVE SOURCES
→ SUPERSEDE OLD ENTRIES
```

### 4. Stronger RCE

Extend the baseline beyond broken references to detect:

- stale canonical ownership;
- missing decision supersession;
- state/task inconsistency;
- evidence older than a relevant project epoch;
- orphaned memory;
- contract/change-manifest inconsistency.

### 5. Git-aware Traceability

Map:

```text
Git diff
→ changed paths
→ task
→ requirement
→ verification
→ evidence
```

This should remain read-only during the first implementation.

### 6. Real Claim Leasing

Add persistent lease timestamps, expiry checks, and optimistic conflict detection for multi-process agents.

### 7. Security Diagnostics

Add a read-only secret-pattern scanner with false-positive-safe reporting. It should never print the secret value itself.

### 8. Runtime Verification Adapters

Allow environment-specific verification adapters without changing the VEE core contract.

## Proposed non-goals for v1.1

v1.1 should not introduce mandatory vector databases, model-specific prompts, automatic semantic conflict resolution, or automatic rewriting of canonical project knowledge.

## Compatibility

All proposed features should be additive. A v1.0 project must remain valid when v1.1 extensions are absent.
